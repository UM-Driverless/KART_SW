- [ ] **`control_task` stalls ~1.1 s then fires 10 iterations back-to-back — the steering PID must run at 500 Hz or better** — Root-caused 2026-07-25. The task averages 8.9 Hz, but the average is a lie: measured at the serial line, steering frames arrive in **bursts of 10 with 0.0 ms between them, separated by 1102 ms gaps** (8 such gaps, 81 zero-gaps, in a 10 s capture). Two causes compound. (1) The AS5600 read blocks for ~1.1 s because nothing is on the I2C bus — that part is expected while the steering sensor migrates to the **MT6701 read as PWM on GPIO 1**, and is not itself the bug to fix here. (2) `KM_RTOS`'s wrapper (`components/km_rtos/km_rtos.c:259`) uses `vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(period_ms))`, which after an overrun returns *immediately, repeatedly*, until `xLastWakeTime` catches up to real time — turning any stall into a catch-up burst. **Cause 2 outlives cause 1**: even with a fast sensor, any transient hiccup produces a burst of PID steps with dt~0, which is worse for a controller than running evenly slow. Work: (a) finish the MT6701 MCPWM-capture path so the sensor read is non-blocking, or failing that give the I2C read a few-millisecond timeout instead of ~1 s; (b) make the wrapper resync `xLastWakeTime = xTaskGetTickCount()` after a detected overrun rather than replaying missed periods; (c) move the compressor and pneumatics out of this task into their own slow task — they need ~1 Hz, the steering needs 500 Hz+, and coupling them means the compressor's requirements ride on the PID's task. Then verify the true rate with the `control_iters` counter in the `ESP_PNEUMATIC` frame, not with frame arrival rate. **The 0.88 Hz pneumatic frame rate is explained by this and is not a separate bug** — the wall-clock throttle correctly sees ~0 ms elapsed inside a burst, so it emits once per burst.

- [ ] **Give the Orin an internet fallback for when the USB tether is gone — mode-switch the radio, or add a dongle** — Today the only way the Orin reaches the internet (and therefore the only way `kart.rubenayla.xyz` and `ssh orin-remote` work) is an iPhone plugged in over USB with Personal Hotspot on. **There is no Wi-Fi fallback and there cannot be one on the built-in radio: the free alternative was checked and ruled out on 2026-07-26, twice over.** First from the driver side — `iw list` on the RTL8822CE prints **no "valid interface combinations" section at all** (196 lines of output, none of them a combinations block), so AP+STA concurrency is not advertised. Then confirmed on the hardware: with the USB cable physically unplugged for 2m 07s while a 5-second-interval logger ran, `wlP1p1s0` stayed `connected:kart-ap` in `type AP` mode for all 112 samples, `type managed` never appeared once, the default route was `NONE` for the whole window, and NM connectivity sat at `limited`. The `kart` AP kept serving the local dashboard at `http://10.42.0.1/` throughout, so an outage costs only internet (`kart.rubenayla.xyz`, `ssh orin-remote`), never the trackside dashboard. It is currently `type AP` on channel 1, and `kart-ap` holds autoconnect-priority 200, so the existing client profiles (`Ruben's iPhone` 100, `8=======D` 90, `iPhone de JBA` 50, `Robots_urjc` 10) can never activate. Read that ruling narrowly: what is impossible on one radio is AP **and** client *simultaneously*.

**Option A — switch the single radio between AP and client mode on cable events. Free, and worth trying before spending anything.** Sequential mode-switching needs no new hardware and is what the Orin did before 2026-07-06, when it joined `Ruben's iPhone` at priority 100. Make it event-driven, never a blind timer: a NetworkManager dispatcher script on `enxfe9ca7a9ecdb` going **down** brings `kart-ap` down and lets the client profiles autoconnect on the priorities already set; if nothing associates within about 30 s it **must bring `kart-ap` back up**, because with neither AP nor client there is no dashboard at all and a bad guess at the track would leave the kart blind. On cable **up**, return to AP so the dashboard sits at a stable `10.42.0.1` whenever the tether is plugged. Two costs to accept: in client mode the `kart` network does not exist, so anyone on it is dropped and the dashboard address becomes whatever the joined network assigns (findable via Cloudflare or the hotspot's client list, but no longer fixed); and the obvious fallback network is the same phone that was meant to be plugged in, so this covers "cable unplugged or broken, phone in pocket" but not "phone absent".

**Option B — add a USB Wi-Fi dongle (~€10) as a second radio.** Strictly better behaviour, at the cost of money and a driver risk: built-in radio keeps beaconing `kart` continuously, dongle joins known networks as a client, no mode-switch state machine, no drop-outs, dashboard address never moves. Pick a chipset with in-tree support for JetPack 6 (kernel 5.15, aarch64) — driver availability is what bites on Jetson, so do not buy on price alone.

**How to test whichever option is built — three cases, and the third is the one that matters.** The test severs the tester's own remote access, because `ssh orin-remote` and `kart.rubenayla.xyz` both ride the Cloudflare tunnel over the tether being unplugged. So instrument first and read the record afterwards rather than trying to watch live: `nohup` a script that appends `nmcli -t -f DEVICE,TYPE,STATE,CONNECTION device`, `nmcli -t -f CONNECTIVITY general`, `iw dev wlP1p1s0 info` and `ip route | grep default` to a log file every 5 s, then pull the cable. Keep a laptop or phone joined to the `kart` Wi-Fi (pwd `umotorsport`) as the local way back in at `ssh orin-local` / `http://10.42.0.1/`, and note `tcpdump` is **not** installed on the Orin if packet-level detail is ever needed. Cases: (1) **known network in range** — unplug with a phone hotspot on and reachable; pass = a client profile associates within ~30 s, the hotspot shows a connected device, `ip route` regains a default via Wi-Fi, and the dashboard answers on the address that network assigned. (2) **cable back** — replug; pass = the default route returns to the tether (metric 100 beats Wi-Fi's 600) and the `kart` AP is back up, so `http://10.42.0.1/` works again. (3) **no known network in range** — unplug with every known hotspot off or out of range; **pass = `kart-ap` comes back up within ~30 s and the dashboard is reachable at `10.42.0.1` again.** Case 3 is the whole safety argument for the design and the easiest to skip, since cases 1 and 2 both look fine while it is broken; a mode-switch that strands the kart with no AP and no client is worse than having no fallback at all. Verify each from the log plus a real dashboard load, not from `nmcli` alone.

Either way the desired priority order — USB tether first, then the phone hotspots, then `Robots_urjc` — needs no new config: the tether's DHCP default route already has **metric 100 against Wi-Fi's 600**, so USB wins automatically whenever it is plugged, and the Wi-Fi profile priorities above already encode the rest. Keep `kart-ap` as the resting state with autoconnect priority above every client profile, so a reboot at the track always comes up with `kart` present.
