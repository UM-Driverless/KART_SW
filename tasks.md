- [ ] **Touching the remote-driving pad jumps straight to that value — a stray tap near the top edge is instant full throttle** — Raised 2026-07-31 while restyling the pad in `src/kb_dashboard/kb_dashboard/index.html`. The pad is absolute: `initJoystick`'s `getAxes` maps wherever the finger lands to the command, so first contact commands it with no travel in between. This is long-standing behaviour that the restyle deliberately preserved rather than changing driving feel unannounced. Two candidate fixes, both a judgement call for whoever drives the kart: (a) make the grab relative — first contact sets an anchor and only movement from it changes the value, so a tap does nothing; (b) keep absolute but add a small centre deadzone (~5%) and rate-limit how fast the throttle axis may rise, which also damps finger jitter on a vibrating kart. (a) is safer, (b) keeps one-tap response. The Y axis is the dangerous one, so limiting a fix to throttle and leaving steering absolute is a reasonable middle.

- [ ] **`control_task` stalls ~1.1 s then fires 10 iterations back-to-back — the steering PID must run at 500 Hz or better** — Root-caused 2026-07-25. The task averages 8.9 Hz, but the average is a lie: measured at the serial line, steering frames arrive in **bursts of 10 with 0.0 ms between them, separated by 1102 ms gaps** (8 such gaps, 81 zero-gaps, in a 10 s capture). Two causes compound. (1) The AS5600 read blocks for ~1.1 s because nothing is on the I2C bus — that part is expected while the steering sensor migrates to the **MT6701 read as PWM on GPIO 1**, and is not itself the bug to fix here. (2) `KM_RTOS`'s wrapper (`components/km_rtos/km_rtos.c:259`) uses `vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(period_ms))`, which after an overrun returns *immediately, repeatedly*, until `xLastWakeTime` catches up to real time — turning any stall into a catch-up burst. **Cause 2 outlives cause 1**: even with a fast sensor, any transient hiccup produces a burst of PID steps with dt~0, which is worse for a controller than running evenly slow. Work: (a) finish the MT6701 MCPWM-capture path so the sensor read is non-blocking, or failing that give the I2C read a few-millisecond timeout instead of ~1 s; (b) make the wrapper resync `xLastWakeTime = xTaskGetTickCount()` after a detected overrun rather than replaying missed periods; (c) move the compressor and pneumatics out of this task into their own slow task — they need ~1 Hz, the steering needs 500 Hz+, and coupling them means the compressor's requirements ride on the PID's task. Then verify the true rate with the `control_iters` counter in the `ESP_PNEUMATIC` frame, not with frame arrival rate. **The 0.88 Hz pneumatic frame rate is explained by this and is not a separate bug** — the wall-clock throttle correctly sees ~0 ms elapsed inside a burst, so it emits once per burst.
    - **Re-measured 2026-07-30 on the kart: the 1.1 s stall is gone.** `ros2 topic hz /esp32/steering` over a 10000-sample window gave **477.1 Hz, min gap 0.000 s, max gap 0.014 s, std dev 0.0030 s** (kart power off, Orin and ESP32 only, firmware at kart-medulla `00e7469`). A 1.1 s gap would have shown up as `max` — it did not, across 10000 samples. The dashboard's own ESP32-link readout agrees, showing 500.0 Hz. So the symptom that opened this task no longer reproduces, and the 8.9 Hz figure above is historical.
    - **What that does and does not settle.** It does not confirm any of (a), (b) or (c) were done — the likely explanation is that the MT6701 PWM path replaced the blocking AS5600 I2C read, removing cause 1, and nobody has checked whether cause 2 (`vTaskDelayUntil` replaying missed periods after an overrun, `components/km_rtos/km_rtos.c:259`) was ever touched. That latent bug turns any future stall back into a catch-up burst, so it is still worth fixing on its own merits. Item (c), moving the compressor and pneumatics out of the steering task, is also still undone.
    - **The residual jitter is real and worth a look before tuning.** At a 2 ms period the gaps should cluster near 2 ms, but `min` is 0.000 s and `max` is 14 ms with a 3 ms standard deviation — so frames still arrive somewhat bunched. That is a much milder version of the same catch-up signature, which is consistent with cause 2 being untouched. **This matters for PID work:** a derivative term behaves completely differently at dt = 2 ms than at dt = 14 ms, and worse when dt is occasionally 0. Anyone tuning kp/ki/kd should know the loop rate is fast but not evenly spaced.
